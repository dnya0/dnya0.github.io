## 🥑 들어가며

동시성 제어 방법을 찾아보면 락, CAS, MVCC 같은 용어가 같이 나온다. 그런데 하나씩 보면 하는 일이 꽤 다르다. CAS는 값이 바뀌었는지 확인하고 저장하는 방식이고, MVCC는 여러 버전 중 어떤 데이터를 보여줄지에 관한 방식이다. 둘을 같이 쓸 수도 있다.

이전에 [트랜잭션과 DB Lock]({% post_url 2024-09-17-Transactional-DB-Lock %})을 정리했는데, 이번에는 범위를 조금 넓혀서 각 방법이 어떻게 동작하는지 살펴보려고 한다. 방 정보 수정과 재고 차감을 예시로 사용했다.

<br>

## 1. 어디에서 동시성을 제어할까?

| 범위 | 다룰 개념 | 핵심 질문 |
| --- | --- | --- |
| 프로세스 내부 | 뮤텍스, 읽기/쓰기 락, 세마포어, 원자적 연산 | 메모리와 자원에 누가 동시에 접근할 수 있는가? |
| DB·저장소 | 조건부 갱신, CAS·OCC, 2PL, MVCC, 타임스탬프 순서 제어 | 읽고 판단한 내용을 어떤 조건으로 저장할 수 있는가? |
| 트랜잭션 보장 수준 | Serializable | 여러 작업의 결과가 순차 실행과 같게 되는가? |
| 여러 서버 | 분산 락, 단일 작성자·Actor | 누가 작업을 맡으며, 소유권이 바뀌면 어떻게 되는가? |
| 복제본 사이의 병합 | CRDT | 각자 변경한 상태를 어떻게 같은 결과로 수렴시키는가? |

같은 시스템 안에서도 여러 방법을 함께 사용한다. 애플리케이션에서 직접 쓰는 락이나 조건부 UPDATE도 있고, DB 내부에서 동작하는 프로토콜도 있다.

<br>

## 2. 다른 요청이 수정한 값을 덮어쓰는 문제

방 상태가 다음과 같다고 가정해보자.

```json
{
  "title": "함께 공부하기",
  "capacity": 4,
  "revision": 5
}
```

요청 A는 방 제목을, 요청 B는 정원을 바꾸려고 한다. 두 요청 모두 기존 상태를 읽고 객체 전체를 저장하면 다음 일이 생길 수 있다.

```text
A: revision 5를 읽음 → 제목을 'CS 공부방'으로 변경
B: revision 5를 읽음 → 정원을 6으로 변경

A 저장: { title: 'CS 공부방', capacity: 4 }
B 저장: { title: '함께 공부하기', capacity: 6 }

→ A가 바꾼 제목이 사라짐
```

이처럼 다른 요청의 변경을 덮어쓰는 문제를 **갱신 손실(Lost Update)**이라고 한다. 저장 명령 하나하나가 안전하게 실행되더라도, **읽기 → 판단 → 쓰기 전체**가 보호되지 않으면 발생할 수 있다.

Redis도 마찬가지다. 명령을 순서대로 실행한다고 해서 애플리케이션이 따로 보낸 `GET → 계산 → SET` 사이에 다른 클라이언트가 끼어들지 못하는 것은 아니다. [Redis 트랜잭션 문서](https://redis.io/docs/latest/develop/using-commands/transactions/)

<br>

## 3. 프로세스 내부: 뮤텍스·읽기/쓰기 락·세마포어

### 뮤텍스: 한 번에 하나만 임계 구역에 들어가기

뮤텍스(Mutex)는 공유 상태를 다루는 코드 구간을 한 작업만 실행하도록 한다. Java의 `synchronized`나 `ReentrantLock`을 예로 들 수 있다. 상태를 읽는 시점부터 변경하는 시점까지 같은 잠금으로 보호한다. [Java Lock API](https://docs.oracle.com/en/java/javase/14/docs/api/java.base/java/util/concurrent/locks/package-summary.html)

```text
lock 획득
  현재 정원과 참가자 수를 읽음
  입장 가능한지 판단
  참가자 추가
lock 해제 (예외가 나도 반드시 실행)
```

모든 관련 코드가 같은 잠금을 사용해야 한다. 요청마다 별도 잠금 객체를 만들면 서로를 막지 못한다. 여기서 말하는 Java 객체 잠금은 같은 프로세스 안의 메모리를 보호하며, 다른 서버의 접근까지 조정하지는 않는다.

### 읽기/쓰기 락: 읽기는 함께, 쓰기는 독점적으로

읽기/쓰기 락은 읽기 전용 작업 여러 개를 허용하되, 쓰기 작업은 다른 읽기·쓰기와 겹치지 않도록 한다. 읽는 동안 상태를 바꾸지 않는다는 규칙을 지켜야 한다.

공유 데이터를 읽는 작업이 많을 때 쓸 수 있다. 다만 읽기가 금방 끝나는 작업이라면 잠금을 관리하는 비용이 더 클 수도 있다. 공정성 정책에 따라 특정 작업이 오래 기다릴 수도 있다. 읽기 락을 잡은 채 쓰기 락으로 전환하는 동작도 구현별 지원 여부를 확인해야 한다. [Java ReadWriteLock 문서](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/locks/ReadWriteLock.html)

### 세마포어: 동시에 들어갈 수 있는 수 제한하기

세마포어(Semaphore)는 허가증(Permit)을 관리한다. 허가증이 3개라면 획득 후 작업하는 요청을 동시에 최대 3개로 제한할 수 있다. 예를 들어 외부 서비스 호출의 동시 실행 수를 제한하는 데 쓸 수 있다. Java 세마포어에는 뮤텍스 같은 소유자 개념이 없어, 획득한 스레드와 반환하는 스레드가 같아야 한다는 제약도 없다. [Java Semaphore 문서](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/Semaphore.html)

허가증이 여러 개라면 같은 데이터에 대한 동시 쓰기는 여전히 가능하다. 따라서 실행 수 제한과 데이터의 상호 배제는 구분해야 한다. 또한 초당 요청 수 제한과도 다르다. 동시 실행 수가 같아도 작업 시간이 짧아지면 초당 처리량은 늘어난다.

## 4. 원자적 연산과 조건부 갱신

단순히 값을 증가시키거나 차감하는 작업이라면, 저장소에서 제공하는 원자적 연산부터 살펴보면 된다.

카운터를 1 증가시킬 때 다음 흐름은 충돌할 수 있다.

```text
GET count → 애플리케이션에서 +1 → SET count
```

Redis의 `INCR`를 사용하면 증가 자체를 하나의 명령으로 처리한다.

```redis
INCR room:42:join_attempts
```

동시에 두 요청이 증가시키면 두 증가가 반영된다. 다만 타임아웃 후 같은 요청을 다시 보내면 다시 증가할 수 있다. **원자성과 중복 요청 방지는 별개의 문제**다. [Redis INCR 문서](https://redis.io/docs/latest/commands/incr/)

관계형 DB에서는 조건과 변경을 한 문장으로 표현할 수도 있다. 다음은 PostgreSQL에서 재고가 남아 있을 때만 차감하는 예시다.

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = 42
  AND quantity > 0
RETURNING quantity;
```

한 상품을 나타내는 행이 하나이고, 같은 규칙을 지켜 갱신한다는 전제다. 반환된 행이 없으면 상품이 없거나 재고가 부족한 경우를 처리한다. PostgreSQL의 Read Committed에서는 경쟁하는 UPDATE가 먼저 끝나기를 기다린 뒤, 갱신된 행에 조건을 다시 평가한다. [PostgreSQL 트랜잭션 격리 문서](https://www.postgresql.org/docs/18/transaction-iso.html)

방 제목과 정원이 서로 독립적이라면 바뀐 필드만 저장하는 것도 전체 객체 덮어쓰기를 피하는 방법이다. 그러나 두 요청이 같은 필드를 바꾸거나, “정원은 현재 참가자 수보다 작을 수 없다”처럼 여러 값에 걸친 규칙이 있다면 추가 제어가 필요하다.

## 5. 낙관적 동시성 제어와 CAS

### OCC: 읽기·계산 후 검증하기

낙관적 동시성 제어(OCC, Optimistic Concurrency Control)는 먼저 읽고 계산한 뒤, 결과를 반영해도 되는지 검증한다. 전형적인 트랜잭션 수준 OCC는 다음 단계로 설명할 수 있다.

```text
읽기·계산: 읽기 집합을 추적하고 변경을 작업 공간에 준비
검증: 다른 트랜잭션과의 충돌 확인
쓰기: 검증을 통과한 변경 반영
```

검증 범위는 행 하나에 한정되지 않는다. 여러 데이터의 읽기·쓰기 집합과 실행 구간을 비교할 수 있다. 검증과 반영 사이에 다시 충돌이 끼어들지 않도록 프로토콜이 조정해야 한다. 읽은 행의 버전만 확인하면 범위 안에 새 행이 생기는 변화까지 자동으로 검출되는 것도 아니다. [CMU OCC 강의 자료](https://15721.courses.cs.cmu.edu/spring2018/notes/04-occ.pdf)

충돌이 적으면 긴 잠금 대기를 줄일 수 있지만, 경쟁이 심하면 이미 수행한 계산을 버리고 재시도하는 비용이 커진다. 아래의 revision 기반 CAS는 이 낙관적 접근을 특정 상태의 조건부 저장에 적용한 예다.

### CAS: 예상한 값과 같을 때만 변경하기

**CAS(Compare-And-Set)**는 현재 값이 예상한 값과 같을 때만 변경을 적용하는 방식이다. revision을 사용하면 데이터의 버전을 비교한다.

```text
A: expected revision = 5 → 일치 → 변경 적용, revision = 6
B: expected revision = 5 → 불일치 → 변경 거절
```

SQL로 표현하면 이런 모양이다.

```sql
UPDATE rooms
SET title = 'CS 공부방',
    revision = revision + 1
WHERE id = 42
  AND revision = 5
RETURNING revision;
```

결과가 없으면 방이 사라졌거나 버전이 맞지 않는 상황이다. 충돌을 구분해서 응답하거나 최신 상태를 다시 읽어 처리한다. 모든 관련 변경 경로가 revision을 함께 증가시켜야 이 검사가 의미 있다.

JPA의 낙관적 락도 이런 버전 검사를 떠올리면 이해하기 쉽다. 읽는 동안 계속 잠금을 잡아두지 않고 저장할 때 충돌을 확인한다. 그렇다고 DB 내부에서 UPDATE를 처리할 때 사용하는 잠금까지 없어지는 것은 아니다.

충돌 후에는 무조건 예전 결과를 다시 저장하면 안 된다. 최신 상태를 읽고 원래 의도를 다시 적용할 수 있는지 판단해야 한다. “현재 정원에 1을 더하기”와 “내가 보던 정원을 6으로 바꾸기”는 재시도의 의미가 다르다.

revision은 과거 상태를 덮어쓰면 안 되는 편집에 유용하다. 반대로 서로 독립적인 변경까지 하나의 방 revision으로 묶으면 불필요한 충돌이 늘 수 있다. 불필요한 충돌이 많다면 버전을 관리하는 단위를 더 작게 나눌 필요가 있다.

## 6. Redis에서 구현하기: WATCH와 Lua

Redis에서는 WATCH나 Lua로 CAS를 구현할 수 있다. 앞에서 본 revision 비교를 Redis로 옮겨보면 다음과 같다.

### WATCH + MULTI/EXEC

```text
WATCH room:42
GET room:42
애플리케이션에서 변경 내용 계산
MULTI
SET room:42 <새 상태>
EXEC
```

읽기 전에 감시를 시작하고, 감시한 키가 실행 전에 변경되면 `EXEC`가 트랜잭션을 실행하지 않는다. 연결에 묶인 상태이므로 실제 코드에서는 같은 연결을 유지하고, 중단·재시도를 처리해야 한다.

WATCH는 명시적인 revision 필드 없이도 키 변경을 감지할 수 있다. 다만 사용자가 오래전에 읽은 revision을 보낸 경우까지 검증하려면 그 revision 비교는 별도로 필요하다. WATCH가 보호하는 것은 감시를 시작한 이후의 구간이다. [Redis의 WATCH 기반 낙관적 잠금](https://redis.io/docs/latest/develop/using-commands/transactions/)

### Lua 스크립트 / Redis Functions

서버 안에서 다음 로직을 한 번에 실행하도록 만들 수도 있다.

```text
현재 방 상태 읽기
→ expected revision과 비교
→ 다르면 실패 반환
→ 같으면 상태 변경 + revision 증가
```

이 경우에는 Lua로 revision 기반 CAS를 구현한 것이다. 반면 revision 없이 “현재 참가자 수가 정원 미만이면 입장시키기”를 검사하고 변경하면, 현재 상태에 대한 원자적 조건부 연산이 된다.

Redis는 스크립트와 함수의 원자적 실행을 보장한다. 실행 중 다른 클라이언트의 명령이 끼어들지 않지만, 긴 스크립트는 다른 요청을 지연시킨다. 또한 오류가 나면 앞선 쓰기를 자동으로 되돌리는 SQL식 롤백을 기대해서는 안 된다. 입력과 조건을 먼저 검사하고 짧게 실행하도록 구성해야 한다. [Redis Programmability](https://redis.io/docs/latest/develop/programmability/), [Redis의 롤백 설명](https://redis.io/blog/you-dont-need-transaction-rollbacks-in-redis/)

Lua로 감쌌더라도 revision 검사 없이 저장하면 오래된 값으로 덮어쓸 수 있다. 위 예시에서 revision을 비교하는 이유다.

<br>

## 7. 비관적 락: 먼저 수정 권한을 확보하기

CAS가 저장 시점에 충돌을 확인한다면, 비관적 락은 필요한 데이터를 잠그고 작업한다. PostgreSQL에서는 다음과 같이 표현할 수 있다.

```sql
BEGIN;

SELECT * FROM rooms WHERE id = 42 FOR UPDATE;

-- 잠근 뒤 읽은 최신 상태로 조건을 검증하고 계산한다.
UPDATE rooms SET capacity = 6 WHERE id = 42;

COMMIT;
```

경쟁하는 수정 요청은 잠금이 풀릴 때까지 기다린다. 일반 SELECT까지 모두 막히는 것은 아니며, 잠금은 트랜잭션 종료 시 해제된다. 보호해야 할 읽기와 판단을 같은 트랜잭션 안에서 수행해야 한다. [PostgreSQL 명시적 잠금 문서](https://www.postgresql.org/docs/18/explicit-locking.html)

충돌 때문에 계산을 계속 다시 해야 한다면, 잠금을 잡고 짧게 끝내는 편이 나을 수 있다. 다만 잠금을 기다리는 시간이 생기고 데드락도 발생할 수 있다. 여러 행을 잠근다면 일관된 잠금 순서를 정하고, 잠금을 잡은 채 외부 API 응답을 오래 기다리는 작업은 피하는 편이 좋다.

사용자가 오래전에 열어둔 화면에서 저장한 경우라면 잠금을 얻은 뒤에도 revision을 비교해야 할 수 있다. 잠금은 다른 트랜잭션의 수정을 막아주지만, 사용자가 보고 있던 값이 최신인지는 알려주지 않는다.

## 8. 2PL: 잠금 획득과 해제 순서

행 잠금을 사용하는 것과, 전체 트랜잭션이 어떤 잠금 규칙을 따르는지는 다른 이야기다. **2PL(Two-Phase Locking, 2단계 잠금)**은 잠금 획득과 해제 순서를 제한한다.

```text
확장 단계: 잠금을 획득할 수 있고 해제하지 않음
                     ↓ 첫 잠금 해제
축소 단계: 잠금을 해제할 수 있고 새로 획득하지 않음
```

필요한 충돌 대상을 올바르게 잠근다는 전제에서 기본 2PL은 충돌 직렬 가능성을 보장한다. 하지만 데드락이나 연쇄 롤백까지 자동으로 막지는 않는다. 예를 들어 A가 X를 잡고 Y를 기다리고, B가 Y를 잡고 X를 기다리면 진행할 수 없다.

**Strict 2PL**은 배타적 쓰기 잠금을 트랜잭션 종료까지 유지하며, **Rigorous 또는 Strong Strict 2PL**은 읽기 잠금까지 종료 시점에 해제하는 방식이다. 문헌별 명칭 차이는 있지만, 어떤 잠금을 언제까지 유지하는지 보면 구분할 수 있다. [CMU 2PL 강의 자료](https://15445.courses.cs.cmu.edu/spring2025/notes/17-twophaselocking.pdf)

2PL은 여러 참여자의 커밋 여부를 조정하는 **2PC(Two-Phase Commit)**와 다른 개념이다. 또한 기존 행만 잠갔다고 범위 안의 새 행 삽입까지 보호되는 것은 아니다. 필요한 규칙에 따라 범위·조건에 대한 보호도 고려해야 한다.

<br>

## 9. MVCC: 여러 버전을 두고 읽기

**MVCC(Multi-Version Concurrency Control)**는 여러 데이터 버전을 관리하면서 트랜잭션에 적절한 버전을 보여주는 방식이다. PostgreSQL의 일반 조회는 스냅샷을 통해 가시적인 버전을 읽으므로, 같은 행을 수정하는 작업과의 읽기·쓰기 경합을 줄일 수 있다. [PostgreSQL MVCC 소개](https://www.postgresql.org/docs/18/mvcc-intro.html)

```text
기존 커밋 버전: title = '공부방'
쓰기 트랜잭션: title = 'CS 공부방'인 새 버전을 생성 중
조회 트랜잭션: 자신의 스냅샷에 보이는 커밋 버전을 읽음
```

어떤 버전이 보이는지는 격리 수준과 스냅샷 시점에 달려 있다. PostgreSQL의 Read Committed는 일반적으로 명령마다 새 스냅샷을 사용하고, Repeatable Read는 트랜잭션 안에서 일관된 스냅샷을 사용한다. **MVCC가 있다는 사실만으로 모든 조회가 트랜잭션 시작 시점에 고정되는 것은 아니다.** [PostgreSQL 격리 수준](https://www.postgresql.org/docs/18/transaction-iso.html)

MVCC와 CAS의 revision은 모두 버전이라는 말을 쓰지만 역할이 다르다. MVCC 버전은 DB가 데이터의 가시성을 관리하는 데 사용하고, 애플리케이션의 revision은 오래된 상태에 근거한 저장을 거절하는 조건으로 사용한다.

MVCC가 있어도 쓰기끼리 충돌할 수 있고, 여러 행에 걸친 규칙이 깨질 수 있다. 잠금이나 충돌 검증과 함께 쓰이는 이유다. 오래된 버전을 회수하는 비용도 있으며, 오래 실행되는 트랜잭션은 필요한 버전의 정리를 지연시킬 수 있다.

<br>

## 10. 타임스탬프 순서 제어

타임스탬프 순서 제어(Timestamp Ordering)는 트랜잭션에 순서 값을 부여하고, 충돌하는 읽기·쓰기가 그 순서에 맞도록 제어한다. 타임스탬프는 꼭 벽시계 시간이 아니라 단조 증가하는 논리적 번호일 수도 있다.

기본적인 단일 버전 방식은 데이터별 마지막 읽기·쓰기 타임스탬프를 관리한다. 예를 들어 다음과 같다.

```text
T1의 타임스탬프 = 10
T2의 타임스탬프 = 20

T2가 X를 읽음
그 뒤 T1이 X를 쓰려고 함
→ T1이 먼저라는 정해진 순서와 맞지 않음
→ 기본 프로토콜에서는 T1을 중단하고 재시도
```

이미 T2가 읽은 뒤 T1의 쓰기를 허용하면, T1 다음 T2라는 순서에서 T2가 봐야 할 값과 달라진다. 그래서 기본 방식은 순서에 어긋나는 접근을 중단시킨다. 단순히 “나중 타임스탬프 값으로 덮어쓰기”와는 다르다. [CMU Timestamp Ordering 강의 자료](https://15445.courses.cs.cmu.edu/spring2025/notes/18-timestampordering.pdf)

기본 방식은 잠금 대기 대신 중단을 선택해 데드락을 피하지만, 재시도와 기아 문제가 생길 수 있다. 실제 프로토콜에는 다중 버전이나 복구 가능성 등을 고려한 변형이 있다. DB 내부에서 읽기와 쓰기 순서를 관리하는 방식이라, 애플리케이션에서 `updated_at`만 비교하는 것과는 다르다.

<br>

## 11. 여러 행의 조건을 지켜야 한다면: Serializable

하나의 행에 대한 CAS만으로 여러 행 사이의 규칙까지 지킬 수 있는 것은 아니다. 예를 들어 “방에는 관리자가 적어도 한 명 남아야 한다”는 조건에서, 두 관리자가 서로 다른 행을 수정해 동시에 탈퇴할 수 있다. 서로 다른 행을 수정하니 각자의 revision 검사는 통과해도, 결과적으로 관리자가 한 명도 남지 않을 수 있다.

이 경우에는 방 행을 공통 잠금 지점으로 삼아 관련 변경을 조정하거나, 모든 관련 변경에 공통 방 revision을 사용하거나, Serializable 격리 수준을 검토할 수 있다.

PostgreSQL의 Serializable은 성공한 트랜잭션들의 결과가 어떤 순차 실행과 같도록 보장한다. 실제로 모든 요청을 하나씩 실행한다는 뜻은 아니다. 직렬화 실패가 발생하면 **트랜잭션 전체를 새로 시작**해야 하며, 규칙에 관여하는 읽기와 쓰기를 올바르게 묶어야 한다. [PostgreSQL Serializable 설명](https://www.postgresql.org/docs/18/transaction-iso.html)

예를 들어 관리자 탈퇴 처리는 다음 범위를 하나의 Serializable 트랜잭션으로 묶는 식이다. 처리 순서를 적으면 다음과 같다.

```text
BEGIN (격리 수준: SERIALIZABLE)
  현재 방의 관리자 목록을 읽는다.
  탈퇴 후에도 관리자가 한 명 이상 남는지 검사한다.
  조건을 만족하면 요청한 관리자의 권한을 제거한다.
COMMIT

직렬화 실패 → 새 트랜잭션에서 읽기와 조건 검사부터 재시도
```

동시에 두 관리자가 탈퇴를 시도해 모두 성공하면 규칙이 깨지는 상황에서는, 관련 작업을 이 격리 수준으로 수행해 두 트랜잭션이 그런 결과로 모두 커밋되는 것을 막는다. 재시도한 요청은 최신 목록을 읽고 탈퇴 불가로 판단할 수 있다.

Serializable이라고 비즈니스 규칙 자체를 DB가 알아내는 것은 아니다. “관리자가 한 명 이상 남아야 한다”는 검사는 애플리케이션이 작성해야 한다. 또한 외부 메일 발송 같은 부수 효과는 DB 롤백으로 취소되지 않으므로, 트랜잭션을 재시도할 때 중복 실행되지 않도록 별도로 설계해야 한다.

중복 가입처럼 저장소의 `UNIQUE` 제약으로 표현할 수 있는 규칙도 있다. 애플리케이션에서 “없네?”라고 조회한 결과만 믿기보다, 저장 시점에 제약으로 지키는 방법을 함께 검토할 수 있다.

<br>

## 12. 분산 락: 여러 서버가 같은 작업 권한을 공유하기

한 프로세스 안의 mutex나 `synchronized`는 다른 서버 프로세스의 요청까지 막지 못한다. 여러 서버가 같은 자원을 다룰 때 공통 잠금 저장소를 이용하는 방식이 분산 락이다.

```text
서버 A ─┐
        ├─ 공통 잠금: room:42 → 잠금을 얻은 서버가 작업
서버 B ─┘
```

하지만 잠금 키를 만들었다고 문제가 모두 해결되는 것은 아니다. 락에 만료 시간을 두면 이런 상황이 가능하다.

```text
A가 락 획득 → 실행이 오래 멈춤
락 만료 → B가 락 획득 후 작업
A가 다시 실행 → 자신이 여전히 소유자인 줄 알고 쓰기
```

락을 해제할 때는 소유 토큰을 원자적으로 비교해 다른 소유자의 락을 지우지 않도록 해야 한다. 오래된 소유자의 쓰기까지 차단하려면 증가하는 **fencing token**을 대상 저장소가 검증하는 설계 등이 필요하다. 임의의 소유 토큰과 fencing token은 역할이 다르다. 장애 조치와 네트워크 지연에 대한 가정도 확인해야 한다. [Redis 분산 락 문서](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

데이터가 이미 하나의 DB에 있고 그 DB의 조건부 UPDATE나 행 잠금으로 규칙을 지킬 수 있다면, 별도 분산 락이 더 단순한 해결책인지는 따져봐야 한다. 서버 수가 많다는 이유만으로 분산 락이 필수가 되는 것은 아니다.

<br>

## 13. 단일 작성자: 같은 방의 요청을 하나씩 처리하기

충돌을 검사하거나 락을 얻는 대신, **같은 방을 수정하는 요청이 하나의 처리 경로를 통과하도록** 설계할 수도 있다.

```text
방 42: 명령 A → 명령 B → 명령 C → 담당 Worker가 순서대로 처리
방 99: 명령 D → 명령 E          → 다른 Worker가 처리
```

방별 큐나 Actor 같은 구조를 떠올릴 수 있다. 전체 시스템을 하나의 스레드로 처리한다는 의미는 아니다. 방 사이에는 병렬성을 유지하면서 같은 방의 변경만 순서대로 처리하는 것이다.

Actor는 자신의 상태를 소유하고 메시지로 작업을 받는 모델이다. 다만 Actor라는 이름만으로 비동기 요청 전체가 서로 끼어들지 않는다고 가정하면 안 된다. 예를 들어 Orleans는 재진입 설정에 따라 한 스레드에서도 서로 다른 요청의 실행 구간이 교차할 수 있다. 사용하는 런타임의 요청 스케줄링 규칙을 확인해야 한다. [Orleans 요청 스케줄링](https://learn.microsoft.com/en-us/dotnet/orleans/grains/request-scheduling)

이때 오래된 상태 전체보다 `제목 변경`, `참가자 추가`처럼 의도를 담은 명령을 보내면 처리 시점의 상태를 기준으로 검증할 수 있다. 오래된 객체 전체를 보내 덮어쓰면, 순서대로 처리해도 앞선 변경이 사라질 수 있다.

장애로 담당 Worker가 교체될 때 이전 Worker의 쓰기를 막는지, 모든 변경이 이 경로를 지나는지 확인해야 한다. 큐의 재전달에 대비한 중복 처리와 상태 저장·처리 완료 확인 순서도 필요하다. 큐를 추가했다고 자동으로 한 번만 실행되는 것은 아니다.

같은 방에서 충돌이 자주 난다면 이런 구조를 생각해볼 수 있다. 대신 인기 있는 방 하나에 요청이 몰리면 그 방의 큐가 밀리게 된다.

<br>

## 14. CRDT: 동시 변경을 병합해 같은 상태로 수렴하기

앞의 방법들이 접근을 조정하거나 충돌을 검증했다면, **CRDT(Conflict-free Replicated Data Type)**는 여러 복제본의 변경을 병합할 수 있도록 데이터 구조와 연산을 설계한다. 필요한 업데이트가 전파돼 같은 업데이트 집합을 반영하면 복제본들이 같은 상태로 수렴하도록 한다. [CRDT 연구 개요](https://arxiv.org/abs/1805.06358)

증가만 가능한 상태 기반 G-Counter를 예로 들어보자. 각 복제본이 자기 몫의 카운터만 증가시키고, 전체 값은 각 항목의 합으로 구한다.

```text
초기 상태: A=0, B=0
복제본 A에서 2회 증가: {A: 2, B: 0}
복제본 B에서 3회 증가: {A: 0, B: 3}

병합: 항목별 최댓값 → {A: 2, B: 3}
전체 값: 2 + 3 = 5
```

이 병합은 순서가 바뀌거나 같은 상태를 다시 받아도 결과가 같다. 상태 기반 CRDT의 병합은 교환·결합·멱등성을 만족하도록 설계한다. 연산 기반 CRDT는 전달 중복이나 인과 순서 등 필요한 통신 조건이 다를 수 있다.

CRDT는 오프라인 변경이나 여러 위치의 독립적인 갱신을 다룰 때 검토할 수 있다. 하지만 **같은 상태로 수렴한다는 것과 모든 비즈니스 규칙을 항상 지킨다는 것은 다르다.** 재고 1개를 두 복제본에서 각각 판매하면 나중에 수량이 합쳐져도 초과 판매는 되돌아가지 않는다. 이런 제약에는 별도 조정이나 권한 분배 등이 필요할 수 있다.

모든 상태를 CRDT로 바꿀 수 있는 것도 아니다. 집합의 동시 추가·삭제, 문서의 동시 편집 등에는 데이터 타입에 맞는 의미와 메타데이터가 필요하다. 따라서 일반적인 CAS나 Serializable을 그대로 대체하는 수단으로 보기는 어렵다.

| 2PL | 잠금 획득·해제 순서 제한 | DB의 잠금 기반 프로토콜 | 데드락, 범위 보호 |
| MVCC | 여러 버전과 스냅샷으로 가시성 관리 | DB의 읽기·쓰기 경합 완화 | 단독으로 모든 쓰기 충돌을 해결하지 않음 |
| 타임스탬프 순서 제어 | 정해진 순서에 맞게 접근 검증 | DB 내부 프로토콜 | 중단·재시도, 변형별 보장 |
| 분산 락 | 서버 사이 작업 소유권 조정 | 프로세스를 넘는 상호 배제 필요 | 만료, 오래된 소유자, 장애 가정 |
| 단일 작성자 | 같은 대상의 명령을 순서대로 처리 | 방·문서 등 대상별 명령 처리 | 병목, 소유권 이전, 재전달 |
| Serializable | 트랜잭션의 직렬 실행과 같은 결과 | 여러 행에 걸친 규칙 | 트랜잭션 전체 재시도와 비용 |
| CRDT | 동시 변경을 병합해 수렴 | 여러 복제본의 독립적 갱신 | 수렴과 업무 제약 보장은 별개 |

Lua와 WATCH는 이 표의 전략을 구현하는 수단으로 이해하면 된다. 예를 들어 Lua 안에서 revision을 비교하면 CAS이고, 현재 재고만 검사하면 원자적 조건부 연산이다.

앞에서 봤듯이 표의 방법 중 하나만 골라야 하는 것은 아니다. MVCC에 충돌 검증을 더해 Serializable을 제공하고, 애플리케이션에서는 사용자 편집 충돌을 잡기 위해 CAS를 추가할 수도 있다.

## 16. 멱등성, TTL, 내구성은 따로 확인하기

동시 요청을 처리하는 방법을 정했어도 다음 항목은 따로 확인해야 한다.

- **멱등성:** 같은 요청이 재전달됐을 때 결과가 중복 반영되는 문제다. 원자적인 증가도 두 번 실행하면 두 번 증가한다.
- **TTL:** 데이터나 잠금의 유효 기간이다. 만료 시간을 설정하는 것만으로 오래된 요청의 쓰기가 차단되지는 않는다.
- **내구성:** 성공한 변경이 장애 이후에도 보존되는지에 대한 문제다. 원자적 실행과는 별도의 보장이다.
- **제약 조건:** UNIQUE처럼 저장소가 직접 검사할 수 있는 규칙이다. 동시성 제어와 함께 사용해 최종 저장 결과를 보호할 수 있다.

상태 변경과 TTL 갱신처럼 함께 지켜야 하는 규칙은 같은 원자적 처리에 묶을 수 있다. 하지만 이 경우에도 “어떤 변경을 허용할지”와 “얼마나 오래 보관할지”는 각각 정의해야 한다.

## 마치며

같은 데이터를 여러 요청이 수정한다고 해도 필요한 처리는 달랐다. 카운터 증가라면 `INCR`로 끝날 수 있지만, 사용자가 열어둔 화면의 수정 내용을 저장할 때는 버전 비교가 필요할 수 있다. 관리자가 최소 한 명 남아야 하는 조건은 행 하나만 검사해서는 지키기 어렵다.

그래서 락을 쓸지 CAS를 쓸지 고르기 전에, 두 요청이 겹쳤을 때 어떤 결과가 나오면 안 되는지부터 적어보면 좋을 것 같다. 충돌한 요청을 기다리게 할지, 실패로 돌려줄지, 다시 읽고 시도할지도 같이 정해야 한다.
